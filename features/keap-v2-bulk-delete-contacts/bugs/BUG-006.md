# BUG-006 — Default 30s timeout applied to ALL v2 operations, not just bulk delete

> Reported: 2026-06-18 | Source: Codex adversarial review (CF-3) | Severity: high
> Status: reported | Bucket: **spec-gap** (spec-conformant-but-undesirable)

## Symptom
A new hard 30s timeout now governs every one of the 343 generated v2 tools, not only the
bulk-delete path it was introduced for.

## Expected
Timeout enforcement scoped to the bulk-delete path (its stated purpose), OR a per-endpoint
timeout policy with verification across latency-sensitive v2 ops.

## Actual
`src/clients/keap.ts` `requestV2()` injects `timeout: 30000` as a default before EVERY v2
request. All v2 tools (list/search/export/write) inherit it. A legitimate call that previously
completed after 30s now hard-fails (ECONNABORTED). Regression evidence sampled only 2 read-only
tools.

## Reproduction
Any slow v2 endpoint (large export/search, degraded upstream) >30s → now fails where it didn't.

## Root-cause hypothesis
plan §1A documented "requestV2 default 30s" to fix the v2-no-timeout gap globally — intentional
but its blast radius (all 343 tools) was under-considered, and no broad latency verification was
done. Spec-conformant to the plan, but the plan decision itself is risky → spec-gap, not a code
divergence.

## Evidence
- src/clients/keap.ts:140-147 (`timeout: 30000` default in requestV2).
- release-readiness regression check covered only keap_list_contacts + keap_v2_list_tags.

## Affects / violated contract
plan §1A / FR-014-adjacent. The global-timeout decision needs amendment → spec-gap.

## Recommendation (needs change-request)
Option A: move the default to `deleteV2` only (requestV2 passes through caller timeout, no global
default) — smallest blast radius, restores "only bulk-delete path timed".
Option B: keep global default but add per-endpoint override + broaden runtime verification across
slow v2 ops.

## Non Production Elements
None. Defect report; no code changed.
