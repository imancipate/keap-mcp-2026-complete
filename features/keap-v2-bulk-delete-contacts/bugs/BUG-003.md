# BUG-003 — Auth-fatal abort discards partial progress (unsafe retry on irreversible deletes)

> Reported: 2026-06-18 | Source: Codex adversarial review
> Severity: medium | Status: **verified** (resolved by CR-001)
> Bucket: **spec-gap**

## Observed
On 401/403, the handler sets `ctl.fatalStatus` (`src/tools/bulk-tools.ts:198`) and then
**throws** a generic auth error (~:212) instead of returning the accumulated `deleted` /
`failed` arrays. Under concurrency, other workers can complete successful deletes before the
auth failure is detected, so the batch may already be partially applied. The caller gets only
an opaque auth error and cannot tell which contacts were removed — dangerous for an
irreversible delete path; weakens incident recovery.

## Expected / violated contract
FR-012 / plan §2.2 step 5 specify: "401/403 → throw a single auth error, regardless of
continue_on_error." The code matches that contract exactly. So this is **not** an
implementation-divergence — the contract itself chose throw-and-discard and never required
returning partial progress.

## Classification rationale
**spec-gap**: partial-progress-on-fatal was never specified. Fixing it (return structured
fatal result with `deleted`/`failed`/attempted/fatalStatus, and/or a preflight auth check)
changes the contract → new scope → route to change-request.

## Affects
- FR-012, plan §2.2 step 5
- src/tools/bulk-tools.ts:196-215

## Recommendation (do NOT apply without change-request)
Return a structured fatal result including partial progress instead of throwing; add a
preflight auth check (single GET) before starting destructive work.

## Non Production Elements
None. Defect report; no code changed.
