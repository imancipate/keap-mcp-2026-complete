# BUG-001 — Rate limiter is per-invocation; concurrent calls can exceed the shared 25 RPS Keap limit

> Reported: 2026-06-18 | Source: Codex adversarial review (branch vs feat/keap-v2-remote-worker)
> Severity: high | Status: reported
> Bucket: **spec-gap** (borderline implementation-divergence vs plan §1A)

## Observed
`handleBulkDeleteContacts()` calls `createRateLimiter(MAX_RPS=10)` **inside each tool call**
(`src/tools/bulk-tools.ts:171`). Each concurrent MCP `tools/call` gets its OWN 10 RPS bucket.
Two–three overlapping calls collectively exceed Keap's 25 req/s/app spike limit (shared across
the worker's single credential), risking 429 storms / throttling of unrelated traffic. The
worker exposes the tool remotely and nothing serializes calls across requests.

## Expected / violated contract
plan.md §1A "Evidence-derived design decisions" states the token-bucket is **the** rate guard
and that the 25 req/s ceiling is **shared across the worker's single Keap credential**. A
per-invocation limiter does not honor that shared ceiling under concurrency.

## Classification rationale
The plan asserted the limiter as the shared guard but never specified cross-request (or
cross-instance) coordination — that requirement was never written. So this is a **spec-gap**:
the multi-concurrent-invocation behavior is unspecified, and the realistic fix (process-global
limiter, or Durable Object / KV-backed leasing for multi-instance) is **new scope**, not
restored compliance. Anchatto: → route to change-request before fixing.

## Affects
- FR-002 (concurrency), plan §1A, plan §2.2 step 4
- src/tools/bulk-tools.ts:171 (`createRateLimiter` per call), 36-46 (MAX_RPS rationale)

## Recommendation (do NOT apply without change-request)
Credential-scoped / process-global limiter for single-instance; shared coordination
(Durable Objects / KV lease) if multiple worker instances serve requests.

## Non Production Elements
None. This is a defect report; no code changed.
