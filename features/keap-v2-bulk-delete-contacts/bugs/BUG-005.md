# BUG-005 — Destructive bulk-delete exposed to every approved MCP client, no kill-switch

> Reported: 2026-06-18 | Source: Codex adversarial review (CF-2) | Severity: high
> Status: reported | Bucket: **spec-gap** (authorization boundary)

## Symptom
After deploy, every OAuth client already approved for this MCP server can call an irreversible
contact-delete primitive — a trust-boundary expansion, not just an additive tool.

## Expected
A destructive capability should be gated: env flag defaulting OFF in prod, and/or a distinct
scope / client allowlist, so prior approvals don't silently gain delete power.

## Actual
`src/register.ts` `getAllTools()` unconditionally spreads `createBulkTools(client)`, and
`dispatchTool` routes `keap_bulk_delete_contacts` with no env gate / scope / allowlist. Live
since deploy (Version e4312d0e).

## Reproduction
Any token valid for /mcp → `tools/call keap_bulk_delete_contacts` → real deletions.

## Root-cause hypothesis
Feature scoped as "additive tool"; the authorization-boundary implication of a DESTRUCTIVE tool
on a shared trust plane was never specified. Release-readiness called the kill-switch "SHOULD" —
understated.

## Evidence
- src/register.ts:24-42 (always-registered), dispatch route at top of dispatchTool.
- release-readiness.md action item 2 (was SHOULD; Codex elevates to ship-blocking).

## Affects / violated contract
No FR specified an authorization boundary for destructive ops → spec-gap.

## Recommendation (needs change-request)
Env gate `KEAP_BULK_DELETE_ENABLED` default-off in prod (registration + dispatch both check it),
or a destructive-scope check / client allowlist. If kept always-on, document as an accepted
intentional trust-boundary change.

## Non Production Elements
None. Defect report; no code changed.
