# BUG-002 — `continue_on_error=false` is not fail-fast at concurrency > 1

> Reported: 2026-06-18 | Source: Codex adversarial review
> Severity: high | Status: **verified** (resolved by CR-001)
> Bucket: **spec-gap** (+ untested-flow)

## Observed
The worker pool reserves IDs and starts deletes in parallel. When one delete fails with
`continue_on_error=false`, `stop` is set, but workers already past the `if (stop || ...)`
check (`src/tools/bulk-tools.ts:182,188`) still run their own `deleteOne()`. For a DESTRUCTIVE
op, a caller asking to stop on first error can still lose up to `concurrency-1` additional
contacts after the first failure.

## Expected / violated contract
FR-008 / plan §2.2 step 6 promise only: "stop scheduling NEW deletes after first failure;
in-flight deletes finish and are still reported." The code matches that literally — so this
is **not** an implementation-divergence. The gap is that the contract is too weak for a
destructive path: it permits in-flight completion and never bounds/forbids extra deletions.

## Classification rationale
- **spec-gap**: destructive fail-fast safety was under-specified (in-flight completion allowed).
- **untested-flow**: the only fail-fast test uses `concurrency: 1`; the concurrency>1 failure
  mode is unexercised (`src/tools/bulk-tools.test.ts` "continue_on_error=false" case).
Both imply new/amended scope + a new test → route to change-request.

## Affects
- FR-008, plan §2.2 step 6
- src/tools/bulk-tools.ts:176-205 (worker loop), bulk-tools.test.ts (fail-fast case)

## Recommendation (do NOT apply without change-request)
Make fail-fast deterministic: force `concurrency=1` when `continue_on_error=false`, OR redesign
scheduling so no new `deleteOne()` starts after the first failure; document any unavoidable
in-flight requests in the result. Add a concurrency>1 fail-fast test.

## Non Production Elements
None. Defect report; no code changed.
